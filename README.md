# TPS Controller

## 0.12.1 local Obsidian fallback

- When **Notification Service → TishOS** is synced to Windows, Linux, or Android, that loaded Obsidian instance now evaluates the same reminder rules and displays the existing clickable Obsidian notices locally. The fallback works in either User or Controller role and never calls TPS Messager/Notifier or ntfy.
- macOS, iPhone, and iPad keep the existing TishOS-native schedule path with no parallel local consumption. The provider remains one synced setting; there is no per-device provider value that could disable TishOS after syncing from another platform.
- Reminder delivery history remains in the existing vault-scoped device-local storage, so one device cannot consume another device's reminders. Provider, role, lifecycle, poll, repeat, and ignore changes still replace the active loop, and **Run Reminder Check Now** evaluates locally when the fallback is active.
- Local Obsidian notices work only while Obsidian is open and active enough to run plugins. They cannot wake a closed or suspended desktop/mobile app and are not operating-system notification-center alerts.
- This adds no setting migration, notification wire change, note/frontmatter field, or background-mobile capability. Focused regressions cover macOS/iOS/iPadOS versus Windows/Linux/Android, User and Controller roles, manual checks, lifecycle replacement, device-local state, Messager bypass, and truthful settings/Notifications-view copy.

## 0.12.0 single-ID native calendar records

- Native calendar records now persist one calendar identity: the standard `tpsId`. New records no longer write `calendarId`, `calendarSourceId`, `calendarUid`, occurrence ID/identity/key fields, recurrence/sync markers, missing timestamps, or speculative companion-path/strategy metadata. `kind` and `tpsSchemaVersion` remain the shared native-record envelope, not additional unique identifiers.
- The canonical `tpsId` is a versioned SHA-256 identity derived from the saved calendar configuration ID and logical occurrence identity. It contains a parseable source scope for safe missing-event handling, does not expose raw feed URLs or UIDs, survives feed URL rotation, keeps non-recurring reschedules stable, and separates recurring occurrences.
- Existing Controller-owned records migrate through GCM nativeRecords API v5. Controller fetches first, freezes the calendar settings and authoritative `{ token, revision, records }` snapshot, then previews the complete create/reidentify/rename path plan. It rebuilds every path-dependent exact payload and submits one GCM-locked batch. GCM checks every native-record kind, malformed/blocked evidence, case-insensitive identity collisions, storage-key collisions, ordered update values, and virtual filename reservations before deterministic writes begin.
- Migration removes the redundant technical fields while preserving body and business properties, ordinary user tags, blank or user-selected workflow status on non-cancelled existing records, and a genuine non-self `associatedNote`. New records default to `scheduled`; an explicit feed cancellation may set `cancelled`. An unresolved path-only relationship is converted into the one public link rather than discarded. Arbitrary manual `calendar-event` notes without positive Controller legacy identity evidence are not adopted.
- GCM reports aligned partial progress if a truly external Markdown/Sync change interrupts separate file commits. Controller immediately rebuilds authoritative state, logs the committed prefix/failed index, and lets the next sync converge. Delayed MetadataCache events cannot replace the frozen snapshot during planning/apply.
- Legacy feeds whose saved configuration lacked an ID receive the exact historical URL-derived fallback ID before settings are persisted, so their existing records remain migratable. Reminder deduplication seeds canonical matches from GCM's authoritative snapshot when MetadataCache is delayed, while retaining legacy evidence during the transition. Conflict-style calendar filenames wait for MetadataCache rather than entering an archive/recreate loop.
- Native calendar mode now requires TPS Global Context Menu 1.48.0 / nativeRecords API v5. Legacy inline-task calendar storage, reminder rules, commands, calendar settings, and minimum supported Obsidian 1.12.0 remain unchanged. Recreating a calendar configuration creates a new source identity; changing its URL in place does not.

## 0.11.8 exact overdue-event audit

## 0.11.6 deterministic bounded reminder repeats

## Silent mobile native-notification publication

- Publishing or replacing a signed TishOS notification schedule is passive and never opens or foregrounds TishOS. This includes removing a future reminder series after a task is completed, deleted, disabled, or filtered out.
- TishOS verifies the replacement file and reconciles Apple's notification queue at its next foreground refresh or system-granted background refresh. Until that refresh, iOS may retain an already-scheduled obsolete request.
- iOS does not expose a supported mechanism for one sandboxed app to wake another app silently or cancel notification requests owned by it. Custom-scheme and universal-link handoffs necessarily foreground their destination, so Controller reserves them for explicit user actions such as pairing, settings, and notification actions.

## Calendar sync

- Calendar sync is single-flight. Overlapping interval, manual, settings, startup, or cross-device triggers join the active physical run; they do not queue a second run. The first caller's force and backfill choices own that flight, and completion/recurrence maintenance emits once after physical reconciliation actually settles.
- Normal calendar sync processes events from today forward. It does not backfill past external calendar events.
- Historical backfill is not part of the streamlined command palette. Normal manual sync uses the current forward-looking sync window.
- `Force Calendar Sync Now` uses the normal non-backfill window.
- Native-record calendar events keep only an existing genuine companion relationship in `associatedNote`; Controller no longer writes companion path/strategy bookkeeping or speculative links. Their clickable `title` self-links the authoritative readable event-record path returned by GCM, so Daily Agenda and other Bases open the existing record, including collision-suffixed paths.
- Task-mode calendar events are written as inline Markdown tasks whose visible title is a native wikilink. The link alias is the event title; its hidden association path is source/UID scoped. Users can choose one linked note per local scheduled day or one shared linked note per recurring series. The link target uses an opaque identity suffix, so its visible alias—not its physical basename—is the human-readable title.
- Blank task target paths write to the scheduled day's Daily Note. A configured single task note keeps every occurrence in that note and reschedules in place. Daily Note tasks that move to another local date are migrated to the newly scheduled day's canonical Daily Note with their indented child block intact.
- When a task-mode event needs a missing daily note, Controller delegates creation to GCM's canonical Daily Note service first so configured Core/Periodic paths, templates, readable titles, and shared normalization are preserved. If GCM is unavailable, Controller merges runtime and persisted Daily Notes/Templates settings, expands core template variables, creates any folders introduced by the date format, and completes Templater before returning a writable file. A configured template that cannot be read or fully processed fails closed instead of creating or writing into a bare note.
- Task-mode calendar events keep external calendar identity in hidden `%% tps-inline-props:... %%` metadata instead of a visible `[tpsInlineProps:: ...]` inline field, so large source URLs/UIDs do not leak into rendered task text.
- Existing task-mode events are reconciled only through their owning checkbox line; Controller never infers the owner by selecting the line before hidden metadata. Frontmatter, fenced examples, and duplicate/ambiguous identities are non-targets. A unique source-scoped UID can repair an ordinary event whose start-derived legacy ID changed after rescheduling; multiple same-UID occurrences remain ambiguous and are never guessed.
- Task-mode creation and updates use atomic file processing. New events are inserted after the leading managed task blocks without relocating nested children or heading-scoped content, and existing mixed/CR-only line endings are preserved. Cross-Daily-Note rescheduling uses target-first insertion, exact source removal, post-write confirmation, and compensating rollback instead of presenting an unconfirmed move as successful.
- Inline calendar tasks participate in identity matching and cancellation but never in file-level orphan cleanup, because archiving or deleting their containing daily/task note would also remove unrelated content.
- All-day inline events use date-only `scheduled` values and no end/duration field. Timed events use the configured duration or end-datetime representation consistently for both creation and later reconciliation.
- External-event reminder matching indexes both event-note frontmatter and inline task calendar payloads, so synced task-mode events are not re-emitted as unmatched external reminders.
- Calendar identity matching scans the whole vault for `externalId`, legacy event id, UID/start, event URL, and title/day matches before creating anything. This prevents duplicate event notes if an existing synced file was moved out of the configured calendar folder.
- Synced event notes use lean frontmatter: Controller does not synthesize `folderPath`, writes `allDay` only when true, and removes that configured field case-insensitively when a previously all-day event becomes timed. Identity, parent links, templates, physical folder routing, and task-line metadata remain unchanged; existing notes are not bulk-migrated.
- Orphan quarantine/delete handling remains limited to configured sync roots and non-ignored paths, so moved notes are recognized for matching without being treated as managed cleanup targets.
- Calendar sync settlement ignores Obsidian/plugin/internal storage paths such as `.obsidian/**`, `.tps/**`, `.trash/**`, and TPS line-base virtual files. Real vault content such as notes and attachments still delays sync until vault events settle.
- The active vault external calendar settings use task-mode daily-note storage with no `Calendar.md` task target, so synced external events become day-scoped task instances instead of being appended to a shared calendar file.

## Two-stage archive

- Controller can move files from a stage-one archive folder into a colder archive folder on a schedule.
- The default rule is safe and explicit: disabled by default, source `Archive`, destination `_archive`, cadence `monthly-end`, run time `23:55`, check interval 60 minutes.
- When enabled, monthly-end runs once per calendar month on the last day of the month after the configured local run time.
- Daily and weekly cadences are also available. Weekly cadence uses the configured weekday.
- The move preserves relative paths below the source folder. For example, `Archive/2026-06-27/Fix.md` moves to `_archive/2026-06-27/Fix.md`.
- Existing destination files are not overwritten. Controller appends a numeric suffix when needed.
- If the destination is configured inside the source folder, files already under the destination are skipped so archived content is not moved deeper on later runs.
- The manual command and settings button run the same move immediately on the controller device.

## S3 attachment upload automation

- TPS Controller uploads active-note local attachments directly to S3-compatible storage. The runtime path no longer depends on S3agle.
- The automation starts on any device where this setting is enabled, so note-open, note-modify, after-command, and manual-command triggers can run from a normal user instance as well as a controller device.
- On Obsidian mobile, Controller intentionally disables the S3 upload/archive service at plugin load time so Node-only S3 dependencies do not prevent the rest of Controller from loading. Mobile can still sync notes and requests; attachment upload/archive should run from a desktop Controller/user instance.
- The automation checks the active note for local attachment embeds/links that resolve to non-Markdown vault files, uploads those files with the AWS S3 client, applies or verifies public access by default, then rewrites the note to public S3-compatible URLs. If public access cannot be confirmed, the upload is treated as failed, the uploaded object is cleaned up, and the local note link is left in place.
- Triggers are user configurable: active note open, active note modify, raw paste events, and a comma-separated list of command IDs to run after. This allows workflows such as running after a Linter command without hardcoding Linter behavior.
- Raw paste handling listens for paste events, lets Obsidian create the local attachment/link, then checks the active note after a short delay. The active-note modify trigger remains as a fallback.
- Upload eligibility is configurable with allowed and ignored attachment extension lists. Ignored extensions win over the allowed list. The current vault config allows image extensions only: `avif`, `gif`, `heic`, `heif`, `jpeg`, `jpg`, `png`, `svg`, and `webp`.
- A manual command and settings button run the same active-note automation immediately.
- S3-compatible settings include endpoint, bucket, region, optional object-key folder, optional public content URL, bucket-subdomain URL mode, public-read ACL toggle, device-local Obsidian SecretStorage references for the access/secret keys, and migrated hash filename settings.
- On load, Controller migrates legacy plaintext credentials from its own settings or `.obsidian/plugins/s3agle/data.json` into named device-local SecretStorage entries. Existing populated secrets are never overwritten: a matching value completes migration, while a conflicting value leaves the legacy field intact and asks the user to select a different secret. Each plaintext field is removed from `data.json` only after its target secret is confirmed; a failed write retains only that legacy field for a later retry and shows a safe notice.
- Access and secret values are trimmed and resolved only when an upload or bucket-archive execution actually needs an S3 client. Missing, empty, unavailable, or conflicting secret references stop the external call and surface a safe notice without logging credential values.
- After a user instance uploads and rewrites the note, TPS Controller writes a controller request containing the note path and confirmed uploaded source paths.
- The controller device fulfills that request after sync by rereading the note. It archives a source attachment only when no remaining local reference in that synced note resolves to the same file.
- Uploaded source files move on the controller device into the configured archive folder while preserving their original path below that folder. Existing archive files are not overwritten; a numeric suffix is appended when needed.
- Each successful Controller upload is recorded in `.tps/s3-upload-manifest.json` with the object key, generated URL, source file, note path, upload time, and last-seen time.
- Optional bucket cleanup is controller-only and disabled by default. When enabled, Controller scans Markdown notes for generated URLs from the manifest. Uploaded objects whose URLs are no longer found after the configured delay are moved inside the same bucket to the configured archive prefix, default `_archive/s3/{YYYY}/{MM}/{DD}`. The effective delay has a 5-minute minimum, and the controller rechecks the URL immediately before moving an object.
- Successful bucket-cleanup runs persist their completion timestamp and suppress another scheduled pass until the configured check interval elapses. Manual, startup, and scheduled callers join an active cleanup rather than duplicating bucket or vault work; a failed cadence save restores the prior timestamp and leaves the next request retryable.
- Bucket cleanup uses copy-then-delete: the original object is deleted only after the archive copy succeeds. Controller does not permanently delete archived bucket objects; manual bucket cleanup can remove archived objects later.
- Manual commands are available for both `Run S3 Attachment Upload Now` and `Run S3 Bucket Archive Now`.
- The feature is disabled by default. It requires endpoint, bucket, and two populated device-local credential secrets before external S3 work can run.
- Legacy internal names still include `s3agleAttachmentAutomation` and `run-s3agle-attachment-automation-now` for settings/command compatibility.

- Task-line reminders are independent reminder entities. A checkbox task with an inline reminder property such as `[scheduled:: ...]` is discovered even when the containing note has no matching frontmatter property, and the task checkbox marker supplies the task entity status instead of inheriting parent note status.
- Reminder rules can independently require or ignore task checkbox states and semantic statuses. The default global ignore keeps completed and wont-do status values ignored, and also ignores `x` and `-` checkbox markers for task rows.
- Reminder task discovery ignores fenced Markdown/code examples, so documentation snippets such as ```md blocks containing checklist syntax do not become actionable reminders.
- Completing a note-level reminder now routes through GCM's guarded status setter when available, so notes with open checklist items trigger the incomplete-checklist modal before `status: complete` is written.
- Open checklist/task lines are reminder targets even when they inherit the note-level reminder date. If task rows match a reminder rule, both the reminder delivery engine and notification view show the actionable task rows and suppress the parent note row for that same reminder.
- Task-mode reminder rows do not show the note status pill. They show a schedule-resolution action instead: explicit inline schedule values are cleared from the task line, note-level schedules are cleared from frontmatter, and inherited note/daily-note task schedules prompt for a target note and move the task block there. Clear scheduled actions require a confirmation modal before mutating reminder metadata.
- Task-mode reminder rows carry the original raw Markdown task line. Move actions send GCM Task API v3 the exact source path, zero-based line number, raw line, and title with `resolution: exact-or-identity` and `sourcePolicy: configured-daily-note`; GCM refuses stale or ambiguous records rather than falling back to a fuzzy title match.
- For a cross-file move from a recognized Daily Note, GCM's configured Daily Note move setting decides whether the source becomes a migrated scratchpad record (`[>]` with `[migratedTo:: [[Target]]]`) or is removed. The move setting is independent of Daily Note schedule inheritance. Non-Daily-Note sources retain the ordinary remove-source move behavior, and Controller continues to exclude retained migrated roots and their nested scratchpad content from reminder discovery.
- The reminder-modal action passes explicit user provenance `{ kind: "user", sourcePluginId: "tps-controller", surface: "reminder-modal" }`. GCM owns any enabled local item-history record; Controller neither writes a parallel journal nor stores history metadata in Controller settings.
- The move picker excludes the source note. Controller requires GCM Task API v3, never calls an older API with the new source policy, never falls back after a move attempt, and removes the reminder row only for a committed success. Missing/older APIs and failed or partial results keep the row visible and show an Obsidian notice; debug logging includes source path, target path, line number, and title breadcrumbs.
- Clearing note-level notification status or reminder snooze metadata deletes only the configured property instead of retaining an empty-string placeholder. Task-line clears continue to remove only their matching inline property.
- Notification sidebar titles render Obsidian markdown links inline when the linked note exists, so task text like `[[Note|Label]]` is clickable only for resolvable vault files. Unresolved wikilinks render as plain text to avoid offering links that create or open missing notes.
- Notification sidebar task rows use a task icon rather than inheriting the containing note/file icon. Note rows still use their configured note icon/color with a `file-text` fallback.
- Notification sidebar actions are overlaid on the right edge so long titles can use the full row width instead of truncating before the action buttons.
- Notification sidebar refreshes are coalesced so metadata events, file-updated events, and action follow-up refreshes do not stack multiple full reminder scans/redraws. The periodic passive refresh runs every 30 seconds, unchanged item sets skip redraw, and slow refreshes are logged when Controller debug logging is enabled.
- Coalesced notification sidebar refreshes compare the row/action display signature, including title fields, note/task labels, icon/color, source and target kind, reminder property source, diff text, and raw task line. Visible row changes therefore redraw even when the underlying file/reminder identity is unchanged.
- The `View Notifications` command and ribbon action reset stale notification leaves, use Obsidian's side-leaf API when available, expand the right sidebar, reveal the notification leaf, explicitly select/focus its tab, and refresh restored notification leaves. UI validation confirms the right sidebar renders the notification empty state (`All caught up!`) when no reminders are due.

## Reminder delivery

- When Batch Notifications is enabled, all reminders triggered in the same run are delivered as one grouped notification.
- Grouping includes timed reminders, all-day reminders, and unmatched external calendar reminders.
- When Batch Notifications is disabled, each reminder is delivered individually.
- Non-repeating vault note/task reminders are delivered only inside a bounded live window after their calculated trigger. The window is twice the configured poll interval, with a one-minute minimum and five-minute maximum; older one-shot triggers are consumed without notification instead of being delivered as stale catch-up alerts.
- `Repeat until complete` rules are exempt from the stale one-shot guard and can continue notifying overdue work at their configured repeat interval. A separate repeating rule does not cause an expired one-shot rule such as `15 minutes before` to fire again.
- **TishOS** is the default for a fresh installation. It projects the same Controller rules into a separate signed schedule for every paired Apple device. On Windows, Linux, and Android, where no TishOS native client exists, the same selection instead runs the local Obsidian-notice fallback while Obsidian is open.
- **ntfy** runs only on the desktop Controller. Each due batch first shows the existing clickable local Obsidian notice, then uses TPS Messager/Notifier when its send API is available. Selecting ntfy also publishes an empty signed TishOS schedule so previously scheduled native work is retired instead of duplicated.
- User-role and mobile instances never own direct ntfy delivery. Role-agnostic TishOS publication remains available from a paired loaded Apple device, while a loaded Windows, Linux, or Android instance may consume reminders only through its local in-app fallback. Local notices cannot wake a closed or suspended app.
- Reminder evaluation is single-flight. Changing role, the master toggle, provider, poll timing, repeat timing, or an ignore filter immediately replaces the effective loop. Ignore-filter edits also refresh open notification views, and in-flight results from the prior policy are discarded before state or delivery.
- Hourly time-tracking reminder delivery is an ntfy provider feature. When TishOS is selected, Controller does not send the parallel TPS Messager hourly alert; TishOS live-tracking presentation remains owned by the paired app/relay flow.

## Cross-device sync request safety

- Replica calendar, reminder, and S3 source-archive requests share `.sync-request.json` for compatibility with existing TPS devices.
- Every new request carries a generation ID. Writes use Obsidian's atomic file processor to merge pending scopes and S3 archive payloads instead of overwriting earlier work.
- Controller polling is single-flight, so a slow calendar or reminder run cannot be started again by the next four-second poll tick.
- Completion atomically acknowledges only the generation that actually ran by replacing it with an empty acknowledgement record. The file is not deleted.
- If another replica merges a newer generation while fulfillment is running, the stale acknowledgement is rejected and the merged request remains pending for the next poll. Previously completed scopes may safely replay, favoring at-least-once execution over lost work.
- If fulfillment throws, no acknowledgement is attempted. The pending request stays intact and the failure is logged for retry on the next poll.
- Legacy request files without a generation ID are normalized to a deterministic legacy generation and remain supported.

## Integration surface

- Controller publishes namespaced workspace events for controller role/settings changes, calendar sync start/completion, reminder updates, and file updates.
- Legacy TPS event aliases remain exported for migration compatibility.
- Controller exposes a plugin API with `isController`, `getRole`, `getSettings`, `getCalendarSettingsSnapshot`, `getReminders`, `getOverdueItems`, and `snoozeFile`.
- Calendar integration uses TPS Calendar Base settings as a fallback source for external calendar definitions and respects Calendar Base hidden-external-event state when building unmatched external reminder candidates.
- Global Context Menu integration is used for shared external identity helpers, file-updated event emission, guarded status writes, parent/child maintenance, and reminder task moves. Reminder-modal moves require Task API v3 so Controller can request GCM's configured Daily Note source behavior and pass explicit-user history provenance; missing or older versions fail closed, while other integrations keep their existing optional/fallback behavior.
- Messager/Notifier integration is used only when **ntfy** is selected. TishOS schedule publication and ntfy dispatch are mutually exclusive provider routes; a future service should join the same provider registry instead of adding another delivery toggle.
- Controller intentionally does not intercept Notebook Navigator file selections. Notebook Navigator and Obsidian determine whether selections reuse the current leaf, open a note, extend a multi-selection, or begin a drag; Controller does not patch global leaf-opening APIs to override that behavior.
