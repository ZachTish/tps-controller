# TPS Controller 2.4.0

Calendar rescheduling now keeps each occurrence tied to its original identity and can update properties on the retained old note, the current note, or both. This is a backward-compatible minor release for the new per-calendar property actions.

## Fixes and behavior

- Group feed components by UID and explicitly attach only that series' exceptions. Previously the iCalendar library could attach an unrelated series' moved instance.
- Select the latest SEQUENCE/LAST-MODIFIED/DTSTAMP revision; collapse identical repeats and reject ambiguous equal-rank conflicts. Repeated master components no longer expand into another series.
- Preserve original recurrence identities for single-instance moves and THISANDFUTURE; an exception carrying RRULE stays an exception.
- Treat malformed, incomplete and expansion-limited feeds as failed fetches, protecting missing-event handling from partial/empty successes.
- Ignore stale revisions of the same component and derive history-generation IDs deterministically, including retries after interrupted retirement.
- Strip recurrenceRule, recurrence and rrule from native calendar templates and managed calendar instances so an already-expanded external occurrence cannot start another local series. Other custom properties and content remain.

## Configure reschedule properties

In **Calendar rules → select a calendar → On external reschedule**, add a property update, choose **Retained old note** or **Current note**, enter its key/value and save. Existing keys are replaced; absent keys are inserted. Values support text, numbers, booleans and JSON lists of text. For example, set old-note `status` to `rescheduled` and new-note `project` to `xyz`.

Old-note actions require **Keep old note when externally rescheduled**. Current-note actions also support in-place updates when preservation is off. Actions run after a baseline when external start/end/all-day timing changes, not on first import, local edits, title changes or cancellation. Repeated syncs preserve later manual property changes. Calendar-owned and identity fields are protected. No existing defaults or commands change. These actions/history apply to Native TPS event records using GCM API v6; legacy note and inline-task storage remain unchanged.

## Validation and limitations

553 tests passed, three existing optional comparison skips, zero failures. TypeScript and the mandatory separate production build passed. Tested final artifacts were deployed and reloaded **only in Obsidian Plugin Test Vault**. Actual settings controls were visually inspected and saved against an isolated disabled fixture. The real parser/Controller/GCM created three recurring notes; moving one produced exactly one replacement, updated the old status, inserted the new project and retained the old body/path/identity. Reordered duplicate input was idempotent and preserved a later manual edit. Synthetic notes were archived and Controller/GCM runtime settings hashes stayed unchanged; outbound automation remained disabled. GCM discovery was scoped to the synthetic folder because unrelated historical QA fixtures intentionally contain identity conflicts.

Minimum Obsidian: **1.12.3**. Mobile CSS wraps/stacks the new controls; physical iPhone acceptance remains user testing. Providers must retain UID/original RECURRENCE-ID. A changed UID or rewritten entire master schedule without exceptions may describe new occurrences; matching is not guessed from titles. Equal-rank conflicts within one feed fail; unchanged revision metadata across separate fetches can still carry legitimate timing changes. Existing production duplicates are not deleted or merged. One designated Controller device should run sync.

**Tested in the test vault and ready for the user's manual BRAT pull. Production was not accessed or updated.** Exact tag: `2.4.0`. Standard `styles.css` includes all UI rules; `styles-ui.css` is optional compatibility material.
