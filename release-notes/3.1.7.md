# TPS Controller 3.1.7

Scope calendar-triggered recurrence recovery to successful applied paths and keep
the reminder-rule filter focused while typing. This is a backward-compatible
patch for desktop and mobile. Minimum Obsidian remains 1.12.3.

## Changes and ownership

- Native calendar sync reports the final handles returned by its validated
  mutation batch. Created, updated, renamed, canceled and archived records use
  their actual applied paths; failed or interrupted batches do not report a
  successful batch. Unchanged syncs do not dispatch recurrence recovery.
- Controller forwards changed paths to GCM's existing single recurrence owner.
  Pair this release with GCM 8.0.0 for scoped work and serialized/coalesced
  overlapping requests. Older GCM remains functionally compatible but may ignore
  the optional scope and scan the full vault after a changed sync.
- No-argument GCM startup recovery and direct completion-driven recurrence stay
  available. Calendar sync no longer incidentally scans unrelated notes for
  recurrence; direct edits outside GCM completion actions retain startup recovery.
  No timer, watcher, cache, retry, mailbox, settings migration or vault remediation
  is added.
- Thrown recovery failures reject the sync caller after logging. GCM drains
  independently queued work once before rejecting joined callers with the first
  thrown error. Existing recurrence creation helpers retain their handled
  Notice/log/false failures; no automatic retry is introduced. A separately queued
  full request can revisit a failed note because it is an independent request.
- Reminder filtering preserves the original input, toolbar, focus, selection and
  listener. Only the results region is rebuilt for typing, no matches and
  clearing. No persisted UI state or reminder evaluation is added.

## Validation

- Focused Controller scope/native-batch tests pass 159/159: unchanged sync dispatch
  and operation counts, exact changed paths, no Controller inventory, roles,
  readiness, failure propagation, actual creates/renames/cancellations/archives
  and exclusion of unchanged owners. The eight newly added controls reproduced
  their failures before the source correction.
- Paired GCM scope/protection/native-record/mutation-owner checks pass 312/312.
  An actual worker plus actual undated tracker creation reproduced two successors
  with queued recovery and stale metadata before the current-source correction;
  it now creates one. Dated creation, full/scoped arrivals, pending full
  supersession, duplicate paths, exclusions, current-source completion/rule
  changes and drained errors are covered. GCM reuses its existing authoritative
  read and unchanged parser; it adds no protection read or deduplication layer.
- Reminder-filter/command-surface checks pass 31/31. The exact released 3.1.6
  renderer fails two of four filter controls by detaching the input. The current
  renderer preserves native-input state in the bounded DOM facade.
- Final versioned Controller suite passes 713/713 with zero failures,
  cancellations or skips, including the three historical notification controls
  against exact released 0.3.5. TypeScript and the mandatory separate
  `TPS_NO_DEPLOY=1 npm run build` pass.
- The ordinary final build deployed to TEST and targeted reload loaded Controller
  3.1.7 alongside GCM 8.0.0. A bounded installed replay uses the actual compiled
  Calendar automation, Controller dispatch, published GCM API, recurrence worker
  and successor creation. Its vault, metadata, atomic mutation, journal and
  daily-note classification boundaries are synthetic in memory:
  - Unchanged sync: zero recovery dispatches, inventories, metadata lookups,
    source reads, writes, creates or journal writes.
  - Two changed ordinary paths: one dispatch, zero inventories, two metadata
    lookups, zero source reads or writes; four bounded path lookups.
  - Full startup: one inventory, 1,000 metadata lookups for 1,000 ordinary notes,
    zero source reads or writes.
  - Queued stale metadata: both `FREQ=DAILY` and `GCM-TRACKER` create one successor.
    Each actual creation replay uses six raw reads, three cached reads, two
    atomic writes and two journal writes against its isolated in-memory host.
- No real notes, recurrence/session state or external providers were mutated by
  the installed replay. No foreground rendering, physical-device latency or
  production speed claim is made from these operation counts.
- Installed native reminder-filter UI verification passes in Obsidian 1.14.4's
  separate, visible Settings window. TEST has no configured reminder rules, so
  the actual installed settings renderer and native controls use two immutable
  synthetic rules and a save/execution owner that refuses writes. Twelve native
  input events and thirteen snapshots keep the original input/toolbar connected
  and focused in their own document, with the expected cursor positions.
  `morning` displays one rule, `zzzz` none and clearing both. Save, restart and
  policy-refresh attempts stay at zero. Cleanup restores the exact original
  settings nodes; real settings identities are preserved. Instrumentation is
  removed, Settings closed and the original leaf restored. No real rules,
  settings or outbound automation are enabled or changed. Native UI correctness
  is verified; this is not physical iPhone testing or a latency benchmark.

The final ordinary production build passed after documentation updates with
byte-identical artifacts and reported the test runtime unchanged. Public
publication is the remaining handoff step for the tested BRAT artifacts. Production installation remains the user's pull and is not claimed.
