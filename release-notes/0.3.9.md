# TPS Controller 0.3.9

TPS Controller `0.3.9` is a backward-compatible reliability and performance patch for the sync-conflict watcher's startup lifecycle. It preserves both released startup-sweep routes while preventing a stopped or restarted watcher from retaining listeners, timers, or stale callbacks that can scan and mutate the vault after Controller has left that lifecycle.

## Changes

- Store listener-specific disposal callbacks and remove Vault listeners through `Vault.offref` and the Metadata Cache listener through `MetadataCache.offref`.
- Own the eight-second startup fallback timer, clear it when metadata resolution wins, and clear it again during `stop()`.
- Bind each startup callback to a watcher generation so captured callbacks from an earlier lifecycle return before enumerating the vault.
- Preserve the existing single-flight sweep guard and allow physical work that already started before `stop()` to settle.
- Add a declared compiled-actual-class lifecycle regression covering both startup routes, emitter ownership, timer cleanup, stop/start generations, a 20,000-file stale callback, and stop during an in-flight rename.

## Preserved behavior

- Metadata resolution still schedules the initial conflict sweep immediately.
- The delayed fallback remains intact for a watcher registered after the Metadata Cache has already resolved.
- Exactly one startup route wins per lifecycle; create and rename monitoring remains active until `stop()`.
- Conflict-name matching, calendar-event identity protection, canonical-note validation, duplicate archive routing, collision suffixes, notices, structured logs, settings, commands, public API, and stored data are unchanged.
- No retry, cache, monkeypatch, setting, command, persistent field, data migration, unsupported Obsidian API, or production-vault dependency is added.
- Controller's unrelated S3 copy-to-get/put provider fallback remains intact because it protects supported S3-compatible providers.

## Before/after evidence

- Exact public `0.3.8` is commit `116112b0cd0087d73de9d048e19ebac5a0e16b03`; its watcher source is SHA-256 `7f2217d778855191ce8bc6692de003ad6113f22484d1e4b8751a3f18d879b9c1`.
- Across 250 active actual-class scenarios totaling 17,341 files, exact `0.3.8` and the candidate produced zero sweep-count, metadata-read, lookup, folder, rename, notice, or final-path mismatches.
- When stopped before a captured fallback ran over 20,000 synthetic files, exact `0.3.8` enumerated the vault once, read 2,322 metadata records, renamed 874 conflicts, left one Metadata Cache listener registered, and attempted one wrong-emitter removal. `0.3.9` performs zero enumerations, reads, lookups, folder operations, or renames and retains zero listeners and timers.
- In a stop/start comparison, exact `0.3.8` allowed both the stale and current fallback to enumerate, whereas `0.3.9` ignores the stale generation and runs only the current fallback.
- Across 31 alternating stopped-workload rounds, median callback time fell from 19.080 to 0.005 ms and p95 from 24.454 to 0.006 ms. These callback timings are environmental; eliminated operation counts are the acceptance gate.

## Compatibility and limitations

- Minimum supported Obsidian version remains `1.12.0`.
- No settings or data migration is required.
- Stopping before the startup sweep begins intentionally cancels that lifecycle's sweep. A later Controller lifecycle gets a fresh Metadata Cache listener and fallback.
- `stop()` does not forcibly interrupt a rename already handed to Obsidian. That operation is allowed to settle so it is not left in an indeterminate partial state.
- The eight-second fallback is still necessary because the Metadata Cache may have resolved before the watcher registers; this release makes it owned and cancellable rather than removing supported recovery behavior.
